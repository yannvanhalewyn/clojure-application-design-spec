Interactive guide to SPEC.md

    Navigability first SPEC §0

    Every rule derives from one priority order. When two rules conflict, the higher one wins.

    1
    Navigability & traceability. From any call site, go-to-definition or one grep reaches the implementation. Direct var references over keyword dispatch; explicit lists over load-order side effects.
    2
    Plain data and functions. Maps and vectors are inspectable at the REPL, printable, diffable, composable.
    3
    Boring, explicit composition. Few composition roots — system config, router, layout — each listing its parts.
    4
    Abstraction only for real repetition, and it must expand to data you could have written by hand.

    Monorepo with services SPEC §1

    One repository, one deps.edn, many services. Services are namespaces (com.company.service-NN-name.*), not separate projects.

    Every service has

    MUST
    main.clj — -main calls run-system! with the service root key. Nothing else.
    MUST
    system.clj — one defmethod per service key (no derive), requires of every ns with needed defmethods.
    MUST
    server.clj — router from feature route tables + the one explicit middleware vector.
    MUST
    resources/system/services/<name>.edn
    MUST NOT
    require another service's namespaces. Shared code moves to com.company.<concern>.

    Domain models & schemas SPEC §4

    The entity namespace (product.cljc) is the model: schemas first, then make, predicates, pure transforms. product.db, product.views, product.routes build on it.

    (def Id
  "(schema) Identifier of a product."
  (m/schema :uuid))

(def Product
  "(schema) A product as read from the database."
  (m/schema
    [:map
     [:product/id Id]
     [:product/name [:string {:min 1}]]
     [:product/audience-type AudienceType]
     ;; Optionally enriched for the UI
     [:product/stream-ids {:optional true} [:set :uuid]]]))

(def UpdateParams
  "(schema) Form params accepted when updating a product."
  (mu/optional-keys
    (mu/select-keys Product [:product/name])))

(defn make [attrs]
  (assoc (select-keys attrs [:product/name])
    :product/id (random-uuid)
    :product/audience-type :product.audience-type/internal))

(defn internal? [product]
  (= :product.audience-type/internal (:product/audience-type product)))
    MUST
    Schema for every domain map: Id, <Entity>, enums, CreateParams/UpdateParams.
    MUST
    Derive param schemas with malli.util; never re-type keys.
    SHOULD
    Reference schemas by var (product/Product), not registry keyword. Registry only for primitive types (:base-url, :secret).
    MUST
    Model fns are pure: no db, request, or clock.
    BoundaryEnforced by
    HTTP paramsreitit :parameters + malli coercion
    System configig/assert-key + throwing coercer
    External payloadsm/coerce at client edge
    Internal fn argsdocumentation only

    Route tables, route data, compiled middleware SPEC §6

    Routes are data. Cross-cutting behavior is a route-data key understood by exactly one :compile middleware, listed once in server.clj. Pick a route and a request to see what mounts and what happens.

    Middleware vector (outermost first)

      Response intents

      Handlers return a Ring response or an intent map; response/middleware renders it.

      KeyProduces

      :res/jsonapplication/json

      :res/no-content204

      Web UI: hypermedia first SPEC §7

      HTMX for ~90% of apps. Check what your app genuinely needs:

      Hypermedia rules

      MUST
      The server decides which actions exist: handlers pass action URLs to views; a view renders an action iff its URL is non-nil.
      MUST
      One URL serves full page and fragment; ::layout/page middleware wraps when HX-Request is absent.
      MUST NOT
      pass the request, router, or db into leaf view components.
      SHOULD
      Shared DOM ids and event names are constants in the owning view ns: layout/PAGE_CONTAINER_ID, modal/CLOSE_EVENT.
      SHOULD
      Cross-component updates via HX-Trigger events.

      Functions and data over multimethods SPEC §8

      Default to data: a map, a vector, case, cond. Routing and middleware are always data. Job handlers and rendering by type MAY use a multimethod when the cases live with their features. Otherwise multimethods only at library extension points (Integrant, Aero, print-method) or true plugin systems.

      Avoid
      Prefer

      If you use a multimethod SPEC §8.3

      MUST
      One composition ns (the service's system.clj or the worker's start ns) requires every implementing namespace.
      MUST
      :default throws ex-info with the dispatch value, or renders an explicit fallback. Never a silent nil.
      MUST
      Dispatch values are grep-able literals: "send-invoice.v1", :field.type/date.
      SHOULD
      Method bodies are one call to a plain function.
      MUST NOT
      use one for routing or middleware.

      Derived keywords SPEC §8.5

      A separate, stricter rule: never derive keys we own, Integrant or domain. Domain hierarchies become explicit sets (#{:role/admin :role/owner}). Only hierarchies a library owns (Duct modules) may be extended.

      Avoid
      Prefer
      The key in the config is the key in the code: grep lands on the method. derive only saves a one-line defmethod per instance.

        Inspecting data with Portal SPEC §11.1

        DJBlue Portal lives in dev/user.clj only. It runs on a fixed port, never opens a window, and prints the URL to visit.

        ;; 1. Start the server + tap target (no browser)
(portal-start!)
;; Portal running at http://localhost:53755 (port 53755)

;; 2. Open http://localhost:53755 yourself; keep the tab.

;; 3. Send values
(tap> (read-config))        ; secrets print masked
(tap> (current-system))
(tap> (product.db/all (db)))

;; 4. Clean up
(portal-clear!)
(portal-stop!)              ; frees the port
        MUST
        Start with portal.api/start {:port 53755}, not open: open launches a window.
        MUST
        Print the URL and port; the developer visits it. The URL never changes, so reload the open tab after a REPL restart.
        MUST NOT
        require Portal from src. Remove tap> calls before committing.
        SHOULD
        Use tap> instead of println/pprint for config, query results, requests.
        One owner per port. A second REPL calling (portal-start!) fails with “Address already in use”: run (portal-stop!) in the other REPL first.
